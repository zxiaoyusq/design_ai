# 代码恢复与缺口补齐

传输层短 ID 先按当前实际请求范围恢复，映射和原始回复均留痕，详见 [紧凑输入](compact-input.md)。图片编码不做该转换。模型负责设计语义判断；JSON、字段、引用、图片编码及来源覆盖一直由代码校验。恢复流程优先复用已经产生且可核验的内容，只把仍需语义判断的原记录交给模型。模型契约为 2.3.0；宿主请求规则版本为 `2.3.0:code-repair-3`，JSON 整理与 `extract_metadata_v5` 元数据整理另存规则版本。

## 允许的 JSON 语法整理

`scripts/json_repair.py` 的 `parse_model_json(text)` 返回解析值和操作列表。原本严格合法的 JSON 原样解析，操作列表为空；不为格式美化重写模型回复。

| 可整理内容 | 必须满足的条件 |
| --- | --- |
| 外围空白、起始 BOM | 只处理 JSON 外壳；字符串正文中的空白和 BOM 保留 |
| Markdown JSON 围栏 | 一个标记为 json 的完整围栏包住整个响应，围栏外只有空白；不从解释文字中挑出局部对象 |
| 尾逗号 | 单次词法扫描，只删除字符串外、已有值之后且紧接对象或数组结束符的逗号；不多轮删除连续逗号 |

整理后必须通过完整严格解析。重复键、NaN、Infinity、浮点溢出产生的非有限值均拒绝；不补括号、引号或缺失值，不修截断响应，不修改正文，不接受多个对象或围栏外散文。语法通过只说明 JSON 可解析，后续仍须验证证据与覆盖。

runner 保留 `result.raw.json` 和 `model_response.raw.txt`；语法有变化时写入 `json_syntax.json`，记录原始文本哈希、解析值哈希和操作。手动 accept 也保存发生语法整理前的原文及 execution.json_syntax。调用者计算原始文本哈希时直接使用原始 UTF-8 内容，不能用解析后重新序列化的 JSON 替代。

## 确定性提取元数据整理

`extract_metadata_v5` 的操作有严格前提，整理后再次走完整模型契约校验。它不推断用户喜欢什么，也不替模型选取新的证据。

| 操作 | 允许条件与边界 |
| --- | --- |
| 删除无依据的图片角色编码 | 记录、字段和连续引文已有效，只删除引文中未完整出现的 image_roles 编码；`303` 不补写成 `P303` |
| 显式长引文无损分段 | 引文超过 600 字且确实为所引字段连续原文，原字段、维度、立场和所有图片角色均合法；只按闭合的完整句末拆成每段至多 600 字、20 个原有角色，片段拼接必须逐字等于原引文，保留片段偏移、来源哈希及原角色。单句过长、尾部不完整、角色无法完整分配或全批观察预算不足时不处理；不修复省略引文、拼接原文或非法标签 |
| 维度去重 | 只去重完全相同的合法维度；不能删除不同维度来满足上限，也不能改写非法标签 |
| 空回答转为 skipped | 原用户回答为空，同一记录全部观察仅为合法 unclear，且没有非空引文、图片角色或 skipped 冲突；保留一次来源覆盖和明确原因，不从问题补证 |
| 顺序列表编号回填 | 显式引文仅缺从 1 连续递增的列表编号；须唯一匹配原文完整连续项，起止为正文边界，恢复的连续原文不超过 600 字；不恢复小数、断号、重复匹配、截半项或遗漏正文、否定词的引文 |
| 相同 skipped 去重 | 同一已知来源的声明都合法，状态和原因完全相同且无 observations 冲突；保留首次位置和删除差异，不合并不同原因或状态 |

除此之外，假引文、错误立场、未知记录、观察/跳过冲突和遗漏来源继续报错。原始模型回复及每项前后差异保留，execution.normalization 记录版本与摘要。代码恢复不清零历史失败计数，也不产生新的模型用量。

## 以完整记录组复用和补齐

该机制只适用于 extract。一个记录组包含同一 record_id 在一次回复中的全部 observations 和 skipped 声明，不能删除该记录的坏项再保留剩余部分。

1. 校验历史尝试是否属于当前正式任务和相同模型配置，核对原请求、实际 messages 和原始回复的摘要。先处理允许的 JSON 语法整理；顶层结构不完整、未知来源或无法归属的项目，不参与该次复用。
2. 按时间从旧到新逐组执行元数据整理及严格单记录校验。每条来源保留最新的完整合法组；较新的失败不会清除先前合法组。保留原记录、原始组、整理后组及其摘要和实际调用来源。
3. 历史合法组已经覆盖全批时，代码直接编译，零模型调用。仍有缺口且已有至少一个合法组时，生成仅含未解决原记录的有效子请求，保留原字段、画像、任务 ID 和剩余观察预算；原正式 jobs/requests 文件不改写。这与 pipeline split 创建正式子任务不同。
4. 补齐回复先按有效子请求校验，再与保留组按原记录顺序编译。最终必须通过原正式任务的完整覆盖、引用、立场及观察总量校验；各组单独有效不代表编译结果自动有效。

若全部记录都没有合法组，不开放额外整批重试。若剩余观察预算不足或无法保持完整来源，也不能通过丢观察、截断原文或重写正式任务来凑出结果。

## 有界调用与恢复

常规内容校验失败上限为 2 次；记录补齐由 `--record-repair-rounds` 独立控制，默认 2，可设 0–2。它是最多两轮有限的缺口调用，不清零原 validation_failures。设为 0 关闭追加补齐调用，仍保留零调用的代码恢复。

传输失败在同一正式任务累计最多 3 次。传输重试沿用上一轮冻结的相同子请求、messages 和补齐轮次，不再消耗新补齐轮次，也不能借记录补齐扩大传输额度。历史次数与补齐轮次跨重启保存；过载退避、冷却与认证错误仍按宿主协议处理。

达到常规校验次数上限并不要求再次请用户批准。已有执行授权内，先运行代码恢复及尚有额度的有限缺口补齐；仍不能完成时保留错误、来源、诊断和续跑位置，不无限重试，也不伪造空结果。

## 编译结果的追溯与用量

`runner/record_repairs/` 保存保留组计划及逐记录诊断；实际补齐调用仍写入 `runner/attempts/`，记录有效子请求、完整模型原文、子请求回复和编译结果。每条复用记录保留原记录与回复摘要、请求与 messages 哈希、模型配置、实际模型和开始/结束时间；补齐来源由该轮真实调用记录追溯。

多次调用编译后的 execution.mode 为 `compiled_record_repair`。它引用各记录来源和编译摘要，不能冒充一个模型在一次上下文中给出的原始回复，也不虚构单一 messages_sha256。因此，这类结果不写入要求单次消息摘要的提取缓存。

input_tokens/output_tokens 只按真实 attempt 统计一次；零调用恢复不增加用量，编译凭证不重复累计原调用 token。原始 outcome、模型原文和失败次数都保留，编译时间单独记录。只有编译结果通过正式任务完整校验并最终完成后续阶段，才按执行协议交付完整研究结果。

# 通用设计趋势归纳

提炼“设计现象 → 用户诉求 → 共同设计原则 → 跨品类应用假设与边界”。保留支持、反对与未选证据，不把资料数量写成市场增长预测。最终由双侧设计主卡和“用研多数人提及、但本轮趋势未覆盖的设计方向”组成。

本包使用 Python 3.10+ 标准库。复制整个目录即可使用；流水线不依赖项目后端、凭据或图片解析库。宿主 Agent 按任务使用自己的文本模型。可选 runner 通过显式提供的适配器调用模型，不绑定服务商。

## 准备与续跑

首次读取[执行协议](protocol.md)。需要判断原文字段、维度或图片关系时读取[证据规则](evidence-rules.md)。每个任务的请求已包含其实际限额、完整输出契约和模板，优先按该请求执行。

确定两个输入 JSON、趋势日期范围和项目根目录。日期仅筛选趋势的 release_time，起止日均包含；用户文本不按日期过滤。未指定日期时使用全部有日期趋势并说明范围；用户说“最近”时将其解析为明确的起止日，不能悄悄按数据最大日期推算。未知日期默认排除，明确允许时使用 --undated include；非法日期报错。

```bash
python SKILL_DIR/scripts/pipeline.py legacy prepare \
  --trends /path/to/trends.json --users /path/to/users.json \
  --project-root /path/to/project \
  --start-date 2026-07-07 --end-date 2026-09-07 --dry-run
```

核对范围后去掉 --dry-run；既有授权已覆盖本地整理时继续执行。代码将本轮过程和最终文件保存到 `data/result/high_trend/<run_id>/`。使用正式 prepare 返回的 `run_dir`，不要使用预览路径。显式 --output 可覆盖默认位置；非空目录不会覆盖。空趋势范围直接生成如实的空结果，不调用模型。

需要缓存时，在 prepare 增加 `--model 实际请求模型 --model-parameters '{"temperature":0}'`，参数应完整描述实际影响输出的配置。未声明模型或使用 --no-cache 时不读取、不写入缓存。缓存只复用用户侧 extract，逐条核对原文、画像、模型配置和提取规则版本；命中仍校验覆盖与原文引用，图片路径从当前输入重新关联。详见协议中的缓存规则。

**2.3 将 extract 输入改为无损表格及短来源 ID。** 新任务使用 2.3；旧运行使用原分发包续跑，不修改其 records/jobs/requests/accepted。完整原文与语义规则不变，仍可复用经过当前校验的已有用户提取缓存；用户要求先看结果时可复用旧证据编译独立预览，不为升级重跑提取。需要理解模型格式、补齐别名或追溯时读取[紧凑输入](compact-input.md)。

## 执行方式

手动宿主循环：

1. `python SKILL_DIR/scripts/pipeline.py next --run RUN`，读取返回的 pending 请求文件。
2. 每个实际请求使用独立文本模型上下文，按 messages 返回一个完整 JSON。独立任务可并行；同一运行的 accept/next/split 写操作必须串行。
3. 保存回复，执行 `pipeline.py accept --run RUN --job JOB_ID --response RESPONSE.json --model ACTUAL_MODEL`。使用缓存时另传 --execution 宿主元信息文件，声明 model_profile 与有效消息哈希；不得用占位模型冒充实际调用。
4. 重复 next，直至 complete=true。仅命令退出码为 0 不代表整轮完成。

需要自动调用、限流和恢复时，读取[宿主适配器协议](host-adapter.md)，使用包内 runner.py。默认并发 2；过载会降低并发并退避，连续拥堵暂停新派发。SDK/适配器内部关闭隐藏重试，统一由 runner 记录额度、原始回复、实际模型、有效 Prompt 哈希、时间和用量。

流程由代码分批推进：**提取 → 用户主题归纳 → 双侧候选 → 候选依据核对 → 分轮合并 → 完整维度反证 → 单卡撰写 → 单卡审核**。

- 提取默认每批最多 32 条来源、64 条观察，并按完整请求字符和预计输出量动态合批；不混不同用户，不截断来源。`--dry-run` 同时返回各批大小与输入字符量，字符数不等于 token 数。
- 提取输入按列发送记录和共享上下文，完整问题及回答不截断；同字段名全批只列一次。原来源 ID 由代码冻结为短 ID，补齐子集继续沿用原短 ID。提取只返回 `record_id/dimensions/stance`，必要时附连续 `quote`、非默认 `field` 和 `image_roles`。短正文无需复述，程序直接恢复完整原文；不同条件、对象或态度需要拆开时仍写明确引文。没有观察的记录必须进入 `skipped` 并说明原因，程序检查完整覆盖。
- 同一用户的画像在每批 `profiles` 中只传一次；不让模型重复输出改写观点、上下文和价值解释。相关维度可共用同一观察，条件与反对意见不得为压缩而合并。
- 主题保存成员来源与条件。候选读取主题摘要及分立场代表，分别写趋势依据、用户依据、共同原则与应用假设；允许零候选，不凑数。
- 候选依据核对使用独立上下文和完整源字段，拒绝牵强交集后再合并。完整反证仍覆盖候选维度全部观察；未被选为代表不等于无关。
- 主题和后续归纳均通过任务级 source_records 读取完整问答，画像通过 profiles[user_id] 读取，分别去重。所有模型只写已有 ID，人数、图片路径、暂缓清单和报告由代码生成。

## 失败与输出

JSON、引用、字段和完整覆盖始终由代码校验。原始 JSON 解析后，代码先按该次实际输入的范围将已知短 record_id 还原；图片编码和正文不参与 ID 替换，未知 ID 仍由严格校验拒绝。校验前允许代码移除完整 JSON 围栏、外围 BOM/空白和字符串外尾逗号，并执行 `extract_metadata_v5` 的确定性元数据整理；显式超长连续原文可在总预算内按完整句末无损分段，并保留全部文字及角色；不猜改引文、立场或正文，不补全截断响应。保留原始回复、前后摘要及操作记录；规则细节见[代码恢复与缺口补齐](code-repair.md)。运行契约为 2.3.0，宿主请求规则版本为 `2.3.0:code-repair-3`；无损传输版本另记 `extract_table_v1`，语义输出规则保持不变。

提取批次失败时，runner 优先复用历史回复中最新的完整合法记录组，只对未解决的原记录生成有效子请求；原正式 job/request 不变。缺口默认最多补齐 2 轮，`--record-repair-rounds 0–2` 可调整，不清零既有校验失败次数；全批没有合法组时不开额外整批重试。历史记录组已能覆盖全批时，代码直接编译并严格验收，无需模型调用。多次调用编译的结果逐记录保留来源，不能冒充单次回复或写入要求单一消息哈希的缓存。

区分服务故障与内容错误。传输失败累计最多 3 次；常规内容失败上限为 2 次，有效记录组的缺口补齐另记有限轮次。传输重试沿用同一子请求与轮次，按 Retry-After 或退避等待。连续 3 次过载/限流暂停新派发，已发出的调用完成后保存。达到常规校验上限不等于需要再次请用户批准；已有授权内先执行代码恢复和有限缺口补齐，仍不能完成时保留问题和续跑位置，不无限重试、不伪造空结果。认证和永久错误不自动重试。

仅在输出过大或截断时拆分未接收的 extract/theme/propose/audit 任务：`pipeline.py split --run RUN --job JOB_ID`。不要为绕过服务故障次数限制而拆任务；单记录不能再拆时保留全文并缩短输出，或在新运行调整预算。

主卡流程 complete=true 后，按[用研补充方向](user-research-gaps.md)处理全部已提取用户证据，先用 `user_gaps.py prepare --run RUN` 生成去重召回与小包，宿主按小包核对语义，最后用 `user_gaps.py publish --run RUN --findings RUN/user_gap_findings.json` 编译输出。代码处理人数、占比、引用、图片路径和最终文件，不新增逐记录模型提取，也不恢复用户已暂停的任务。

交付前读取 `report.md`、`high_potential_trends.json`、`validation_report.json`。主卡 completion 标记和用研补充状态分别检查：存在 completion.json 且 user_research_gaps_status=reviewed 才表示两部分均完成；空趋势范围未进行用户提取时如实说明不可评估。输出不包含“下一轮验证”或 validation_questions。用研补充按去重用户提及超过统计分母的一半筛选，不能替换成未入选文章清单；不足多数或趋势覆盖未核对完整时不凑数。交付真实文件链接、资料范围与图片缺口。

## 证据边界

- 输入全部为文本，不读取像素、不发送图片、不访问输入 URL；--include-vl-text 只纳入已有视觉分析文字，默认关闭。
- 问题只提供上下文，回答才是用户证据；保留原品类、比较对象、否定、条件及概念/原型状态。未明确表达的 user_value 留空。
- 相同用户多条记录只计一人，无归属需求不计人数、不能替代用户侧依据。不同文章 ID 不等于独立项目；跨品类应用始终为待验证假设。
- 图片仅按文章来源或同一用户、当前引文明确出现的编码关联。程序从当前来源补编码和路径，未判定的角色保留 unclear。image_roles 区分 target/comparison/reference/unclear；整条证据为反对关系，不能推出比较图片不受喜欢。输出不从该关系推断图片态度。
- 最终模型审核与人工确认分开；human_review_status 初始为 pending。
- 不自动联网。用户要求外网扩展时可另附来源与日期，不把未进入本包证据契约的网页混入本轮统计。

耗时核对：runner 每次停止或完成都会生成 `performance_report.json`，分别列出各阶段单次耗时中位数/P95、总调用时间、失败调用耗时与已知用量。也可执行 `pipeline.py performance --run RUN` 汇总旧 host 或新 runner 日志。并发调用时间之和不等于实际等待时间；未运行阶段和缺失时长不可记成零。

本地验证：`python -m unittest discover -s SKILL_DIR/tests -p 'test_*.py'`。测试使用临时数据及假适配器，不需要付费模型或图片内容。

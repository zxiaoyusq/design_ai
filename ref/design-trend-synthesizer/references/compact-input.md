# 提取输入的无损压缩

2.3 只调整 extract 的模型传输格式，语义判断、原文、字段及最终证据结构不变。`jobs/records` 保存完整来源，模型只看到表格及当前批次短 ID；后续主题、成卡等阶段继续使用原有结构。无需 Agent 自行压缩或修改请求，`prepare`、预算预览、runner 和补齐子集都调用同一消息生成函数。

## 发给模型的内容

- `payload.record_columns` 定义记录行：`[id, context, answer]`。短 ID 如 r1，context 是共享上下文的零基下标，answer 保留原回答全文；不截断、不摘要。没有第三项表示字段缺失，第三项为 null 表示源值确为 null。
- `context_columns` 定义上下文行。每列为 `[区域, 字段名]`，record 区域保留 kind、user_id、release_time 等记录信息，fields 区域保留 question、scenario_type、question_type、answer_type 及其他原字段。meta.answer_field 指出回答对应的原字段，meta.profile 指向画像。字段名全批只列一次，完整相同的上下文只存一行。
- `context_missing` 单独记录原来不存在的格子，与原值 null 区分；`meta.fields_absent` 保留整个 fields 字段缺失的情况。未知额外字段也保留，不按猜测删去“可能没用”的语境。
- `profiles` 每个用户只写一次。编码或图片路径不由模型生成，图片编码如 P12 保持原样。

每份模型消息自带解读规则和输出模板，模型仍输出 `job_id/observations/skipped`；observation/skipped 的 `record_id` 使用输入行的短 ID。其它输出字段及约束不变。不要把输入行数组原样当成模型输出，也不要将短 ID 应用到引文里的图片编码。

## 接收、补齐与缓存

原任务创建时，代码把短 ID → 完整来源 ID 冻结到私有 `transport_aliases`；模型输入不含此完整映射。短 ID 与任何规范 ID 都不重名，重复来源 ID 明确报错。补齐子集继承原映射，即使只剩原第 3 条，也继续用原短 ID，不重新从 r1 编号。

接收顺序是：严格 JSON 解析及有界语法整理 → 按**该次实际请求的记录范围**还原 ID → 原有元数据整理 → 原契约及逐字引文校验。只改变 observations/skipped 中已知短 record_id，原规范 ID 保持不变；未知 ID、错误字段、图片编码和证据正文不猜改。内部接受凭证、缓存、整记录复用与最终证据继续使用规范 ID。

手动 accept 的 `original_response` 保留模型原对象；runner 保留 raw 原文，并在 normalization 中的 transport 记录传输版本、映射摘要、逐项 ID 还原及解码结果摘要。历史复用也先按每个 attempt 的有效子集解码，不能拿整个原批去解释子集回复。服务重试继续使用冻结消息及别名，保留原失败次数与用量。

2.3 使用新运行，旧运行继续由原版本包处理，不覆写已保存的 requests/jobs/accepted。旧用户提取缓存仍按未改变的语义规则、原文、画像和模型配置校验后复用；缓存键不因纯输入排版变更而整体失效。编译的多次调用凭证仍不能冒充单次回复写入要求单一消息哈希的缓存。

## 成本与边界

默认仍为每批至多 32 条来源、64 条观察，保留输出规模限制。压缩减少输入字符，不承诺原批次数、实际 token 或时间按相同比例下降。小批次的列定义和解读说明有固定成本，可能略大于原格式；后续是否改变批大小，应另外根据真实模型输出稳定性判断，不因字符减少自动扩大输出。

以现有 149 批、4,181 条来源做同批离线对照，完整消息字符减少约 21.9%；707 字回答的真实 32 条批次从 9,987 降为 6,456 字符。以上是包含系统说明和输出模板的字符数，不是服务商计费 token。旧接受回复的代码回放只证明映射和验证链路保真，不能替代新模型质量或延迟实测。

# 用研语义聚类 v1

本方法对已有来源记录做语义归纳，再用程序校验和汇总。语义判断由分析助手读取全文后完成；Python程序不通过关键词命中或预置人名替代语义判断。本次没有调用嵌入模型、K-means或外部模型API。

## 输入与产物

输入为按人整理的semantic-units.jsonl，附人物表、原始文字、图片出现关系及展示版本。原始证据冻结不改。

输出包括主题簇、逐条归属及理由、未聚类/语义不足记录、人物去重统计、正向/边界/替代方案/概念举例分支、关联图片，以及可供下一步趋势握手消费的输入。输出不等于趋势排名或设计执行批准。

## 可复用步骤

1. prepare.py保存输入摘要、方法版本、文件哈希和完整阅读包。
2. 分析助手按prompts/cluster.md阅读全文，提出语义主题。不同数据可得到不同主题和数量。
3. 多义表达允许分量归属多个主题，但每个归属须有准确引用、完整原文和归属理由。保留同句的组合和限制，不把分量变成独立硬约束。
4. 直接设计偏好、品牌印象、个人愿望和被要求举例的概念使用不同证据通道。纯品牌名/账号名不自动解释为风格。
5. 由compile.py执行引用、人物、态度和覆盖检查，生成统计及图文回链。人数按person_id去重；跨主题重叠不表示人群互斥。
6. 按prompts/review.md核查边界反例与过度概括。当前同一助手的自查不是独立语义复核。
7. 发布聚类浏览页，保留原始按人浏览页。原图及图片关联不因进入主题簇而升级可信度。

## 簇与证据的区分

- shared_theme：本批至少两位受访者的设计偏好涉及一个可解释主题。簇内可保留不同分支，不声称所有人表达完全同一含义。
- exploratory_signal：只有一位受访者的明确设计线索。保留为探索，不强并成跨人共性。
- design_issue：把同一设计问题中的喜欢、排斥、替代方案与未明确值的表达放在一起供比较，不作为统一偏好方向。
- background_theme：个人期望、人物品格或品牌使用价值等背景。它们不能直接证明外观偏好。

每个归属的relation为support、boundary、alternative、context、illustration或mention。boundary保存具体反例或限制，不自动变成“反对该主题”的人数。品牌印象单独统计；概念举例、人物愿望和仅提及某个属性不计直接支持票。

## 关键保护

“太亮”仍是带程度的具体排斥；“多彩但平静”两部分均保留；“哑光”不会因另一条谈光泽就被当作反对一切光泽；“未选择”不变成dislike；“喜欢品牌”不证明喜欢某种视觉风格或产品性能。

场景未记录时保留未知，可先归纳宽主题。相机、背板、颜色、整图和参考组的对象范围不混同。具体DNA参数或数值的解释留给后续阶段。

## 复跑与复用

    python prepare.py --dataset <数据目录> --output <新运行目录>
    # 分析助手读取阅读包和提示词，写入source-bound proposal.json。
    python compile.py --dataset <数据目录> --proposal <proposal.json> --output <新运行目录>
    python verify.py --dataset <数据目录> --run <新运行目录>

新数据必须重新做语义判断。当前运行的analyst-proposal.json是这批资料的分析结果，不能当作另一批人的分类规则复用。所有输入和方法有哈希，任何修订另存版本。

verify.py为数据集无关的完整性验证。verify_case_20260929.py是本批167条记录的具名反例回归，包含固定ID和本批预期；它是案例测试，不能拿其人数或主题数量要求新数据。
